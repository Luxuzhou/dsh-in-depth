    第8章 Web、SDK 与部署形态¶

    学习目标¶

    了解DSH的Web、Headless、ACP和SDK表面，能够把开发者本机实例与企业多用户服务区分开，并设计可迁移部署架构。

    8.1 同一运行时，多种表面¶

    官方仓库提供Web UI、一次性Headless运行、ACP自动化示例和JSON-RPC/Python SDK。它们复用Harness能力，但面向不同调用者：人类交互、脚本任务、编辑器或外部服务。

    Browser / CLI / IDE / Service
              ↓
        Surface Adapter
              ↓
      Agent + Session Runtime
              ↓
 Tools / Workspace / Providers

    界面不应成为领域能力的唯一入口。稳定业务能力通过服务接口暴露后，Web、DSH插件和其他系统才能复用。

    8.2 本地Web不等于企业Web¶

    npx @deepseek-ai/dsh web默认在本机启动Web UI，适合个人使用与开发。把监听地址改为局域网并不自动获得企业能力，还缺少：

    • 统一身份认证与用户生命周期；
    • 会话、工作区和工具的租户隔离；
    • TLS、反向代理和安全响应头；
    • 多实例状态存储与并发控制；
    • 配额、成本、审计、备份和灾难恢复；
    • 插件安装与升级的集中治理。

    8.3 推荐的企业分层¶

    浏览器
  ↓ HTTPS
网关：认证、限流、审计关联ID
  ↓
应用服务：会话、审批、业务状态
  ↓
DSH运行层：Agent Loop、工具编排
  ↓
领域服务：语义、权限、确定性执行
  ↓
数据库、文件、模型与外部系统

    若每家医院独立部署，可保持同一镜像和代码版本，把医院差异放入受版本控制的Profile、语义包和密钥配置。浏览器无需安装，升级集中在院内服务器，迁移性通常优于厚Electron客户端。

    8.4 API设计要保存Agent语义¶

    普通“发消息/收文本”接口不足以支持Agent产品。服务接口至少需要表达：会话创建、消息追加、流式事件、运行状态、取消、审批请求、审批执行、轨迹查询和结构化错误。

    审批凭证应绑定用户、租户、会话、计划摘要、有效期和一次性状态，避免用户确认A计划后系统执行已经变化的B计划。

    8.5 可观测性¶

    建议贯穿一次任务的关联ID：HTTP请求、会话、turn、step、模型请求和工具调用都可追踪。核心指标包括：任务成功率、工具错误率、首次动作延迟、总step、模型token、审批拒绝率、取消后残留工作和不同版本的回归差异。

    8.6 升级策略¶

    DSH仍处于Developer Preview。生产集成应固定提交或发布版本，在适配层后使用；升级通过影子流量或回放集验证，再灰度部署。业务领域接口不要直接暴露大量DSH内部类型，以降低框架变化的影响。

    本章小结¶

    Web提升的是交付和集中运维能力，不会自动完成多租户生产化。企业应把DSH放在稳定API和领域服务之间，通过适配层隔离快速变化。

    思考题¶

    1. 本地浏览器访问localhost为何不一定比Electron更易迁移？
    2. 哪些会话事件应该实时推送，哪些应由客户端按需查询？
    3. 多实例部署时，Agent运行所有权如何避免重复执行？

    求职面试题¶

    设计一个院内部署的多用户Agent Web服务，说明认证、会话路由、审批、状态存储和升级方案。
