    第3章 Agent Loop 与一轮任务的生命周期¶

    学习目标¶

    能够区分turn与step，解释inbox、模型请求、工具执行和停止检查点的关系，并从事件轨迹定位失败发生在哪一层。

    3.1 Turn 和 Step¶

    在DSH中，一个step包含一次模型请求以及由该响应触发的工具调用；一个turn从领取用户输入开始，可以包含零个或多个step，直到系统不再欠下一次模型请求。

    turn/start
  claim input
  step/start
    user/message
    assemble prompt + tool schemas
    model request
    assistant/message
    tool/call → tool/result
  step/end
  ... possible next step ...
turn/end

    这个区分解决了一个常见误解：一次用户发言并不只对应一次模型调用。工具结果需要再次交给模型时，系统仍在同一个turn中推进新的step。

    3.2 Inbox 与中途引导¶

    输入通过Agent inbox进入驱动器。用户在任务执行过程中追加的消息可能成为下一step输入，而不是粗暴终止当前进程。DSH同时区分待领取输入、已经领取的消息和实时状态，使UI或SDK能够显示正在发生什么。

    这种设计为steering提供了基础，但业务产品仍需定义语义：新消息是补充条件、修正目标还是取消任务，不能完全依赖时间顺序猜测。

    3.3 请求之前发生什么¶

    每个step并不是直接把聊天记录发给模型。驱动器先经历：

    1. agent/pre-step：允许插件拒绝或改写即将进入的消息；
    2. 从会话日志派生模型历史；
    3. 组装系统提示片段和当前可见工具Schema；
    4. agent/request和llm/stream：让适配器发起流式请求。

    因此，上下文压缩、Skill目录、工具作用域和运行策略都可以在不修改核心Loop的情况下介入。

    3.4 工具执行并非简单函数调用¶

    模型返回工具调用后，DSH先判断工具是否可以并行，再经过有序的pre策略、执行包装器、工具本体和post策略。调用与结果写入会话日志，UI则消费实时事件和持久事件进行展示。

    工具失败通常被物化为结构化结果，让模型有机会修复；进程崩溃、会话损坏或Provider不可用则属于不同故障域。生产监控需要区分这些错误，否则“Agent失败率”无法指导改进。

    3.5 如何停止¶

    当模型自然结束且没有新的下一步输入时，系统进入agent/turn-stopping检查点。插件可在这里判断是否仍有未完成工作。随后写入turn/end并把Agent状态置为空闲。

    自主性不等于无限循环。成熟部署应限制最大step、总耗时、工具预算和成本，并明确触发限制时返回什么证据。

    3.6 用轨迹做故障归因¶

    按顺序检查：

    • 没有turn/start：输入或Agent激活失败；
    • 有turn无step：pre-step拒绝或输入被改写为空；
    • 有step无assistant message：模型请求或流式适配失败；
    • 有tool call无result：工具执行、取消或进程生命周期异常；
    • 多次重复调用：模型策略、工具描述或停止检查点可能有问题；
    • 最终回答错误但执行正确：结果解释或业务语义层有问题。

    本章小结¶

    Agent Loop是状态推进器，而不是一条while循环。理解turn、step、inbox、实时事件和持久事件，是调试多轮自主行为的起点。

    思考题¶

    1. 用户在工具执行期间发送“不要改了，只分析”时，应在哪个阶段处理？
    2. 为什么工具错误最好成为模型可见结果，而不是直接让进程退出？
    3. 如何区分模型没有停止和系统仍然欠一个必要步骤？

    求职面试题¶

    给出一段“模型连续三次调用同一工具”的轨迹，请列出至少四种可能原因及验证方法。
