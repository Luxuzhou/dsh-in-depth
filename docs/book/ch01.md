# 第1章 从模型到 Harness

## 学习目标

完成本章后，你应当能够区分模型、Harness、Agent 和业务应用，解释 DSH 的最小组成，并用一张运行图描述用户请求如何到达外部世界。

## 1.1 四个经常混用的概念

**模型**接收消息并生成文本或工具调用，它本身不拥有文件、终端和数据库。**Harness**负责组织消息、暴露工具、驱动循环、保存状态并处理失败。**Agent**是模型在某个 Harness 和运行环境中的具体行动主体。**应用**则继续增加用户界面、权限、业务规则和部署运维。

```text
业务应用
└── Agent
    ├── 模型
    ├── Harness
    │   ├── 上下文组装
    │   ├── 工具执行
    │   ├── 会话与循环
    │   └── 策略与观测
    └── 外部环境
        ├── 文件与进程
        ├── Web 与 MCP
        └── 企业 API
```

当模型相同而工具描述、上下文裁剪或错误恢复策略不同时，Agent 的实际能力可能显著不同。这就是 Harness 工程值得独立研究的原因。

## 1.2 DSH 的最小心智模型

DeepSeek Harness 把一个运行实例组织成 Cordis 插件树。模型适配器、工具注册表、会话、Agent Loop、Web 界面乃至审批策略都通过插件贡献能力。官方将这一原则概括为“Everything is a Plugin”。

从产品角度，可以把 DSH 看成五层：

| 层 | 责任 | 代表能力 |
|---|---|---|
| 表面层 | 与人或系统交互 | Web、Headless、ACP、SDK |
| 控制层 | 推进任务 | Agent、Agent Loop、Plan、Goal |
| 上下文层 | 决定模型看到什么 | System Prompt、Session、Compaction、Skill |
| 行动层 | 改变外部世界 | Tools、Shell、FS、Web、MCP、Workflow |
| 基础层 | 组合与生命周期 | Cordis Context、Service、Event、Effect |

这些层是理解关系的教学模型，不等于源码中的固定目录。真正的源码边界要以服务、事件和依赖为准。

## 1.3 一次任务为什么需要循环

普通聊天通常是一次请求、一次响应。Agent 任务可能经历多次模型调用：

```text
用户任务 → 模型决定读文件 → 工具返回文件
        → 模型决定修改文件 → 工具返回差异
        → 模型决定运行测试 → 工具返回结果
        → 模型给出最终答复
```

这里的关键不是“多调用几次模型”，而是每次调用前都要从会话事件重建可信历史，确保工具结果与当前状态一致，并在取消、审批、超时或上下文溢出时得到确定行为。

## 1.4 DSH 能做什么，不能替代什么

DSH适合作为插件化 Agent Runtime：它提供组合、会话、工具、工作区、Web和自动化接口。它不自动提供某个行业的业务语义，也不会天然满足企业的身份、租户、审计和合规要求。

以智能问数为例，DSH可以负责多轮会话和工具编排；指标口径、字段映射、查询权限和确定性SQL仍应由领域服务负责。把这些职责分开，既能利用Agent自主性，又不让模型成为数据正确性的唯一来源。

## 本章小结

DSH不是模型包装器，也不是完整业务应用。它位于两者之间：通过插件化 Harness 把模型、上下文、工具、状态和产品表面组合成 Agent。
