# 第2章 Cordis 微内核与插件树

## 学习目标

理解插件、Context、Service、依赖注入、事件和可逆副作用，并能判断一项新功能应当注册在哪里。

## 2.1 为什么不是一个巨大的 Agent 类

如果所有能力都写进一个 Agent 类，模型、工具、存储、UI和沙箱会形成互相引用。任何替换都需要修改核心循环，测试也难以隔离。Cordis选择让插件向共享Context贡献服务和事件，消费者通过稳定的服务键寻找能力，而不是导入某个具体实现。

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'example-plugin'
export const inject = ['tools']

export function apply(ctx: Context) {
  // required services are ready here
}
```

最小插件只是一个带 `apply(ctx)` 的模块。`inject` 声明它依赖哪些服务；Cordis等待依赖就绪后再挂载插件。

## 2.2 Context 是能力目录，不是全局变量包

`ctx.tools`、`ctx.llm`、`ctx.sessions`等键提供稳定访问点。它们看起来像全局对象，但Context可以派生作用域，因此同一进程中的不同Agent可以看到不同工具或Provider。正确问题不是“我能否从ctx拿到服务”，而是“该服务应当对哪个作用域可见”。

## 2.3 Service Definition、Provider、Consumer

DSH把一项可替换能力称为 capability seam，完整设计包含三种角色：

1. **Service Definition**声明调用者依赖的接口；
2. **Service Provider**提供本地、远程或沙箱实现；
3. **Consumer**把能力转成工具、界面或其他业务行为。

例如文件系统能力可以由本机Provider或远程沙箱Provider实现，Shell、LSP等消费者仍然面向同一服务。当替换Provider时，能力整体迁移，而不是每个工具分别改造。

## 2.4 事件的四种分发语义

| 模式 | 用途 | 心智模型 |
|---|---|---|
| `emit` | 广播事实 | 多个观察者独立接收 |
| `waterfall` | 包装或改写一次操作 | 必须调用 `next()` 才继续 |
| `parallel` | 并行等待多个处理器 | 所有结果共同完成 |
| `serial` | 有序执行检查点 | 一个接一个完成 |

工具执行前策略适合waterfall，因为插件可以允许、拒绝或请求审批；会话事件广播适合emit，因为日志事实不应被监听者否决。

## 2.5 注册即副作用，卸载必须可逆

插件可能注册工具、监听事件、启动定时器或打开连接。DSH要求这些注册成为Cordis effect，使热重载和卸载能够撤销旧行为。框架管理的 `ctx.on()`、注册表返回的disposer和 `ctx.effect()` 都服务于这一目标。

```ts
export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 5_000)
    return () => clearInterval(timer)
  })
}
```

如果插件重载后出现重复工具、重复事件或孤儿进程，首先检查副作用是否真正归属插件生命周期。

## 2.6 如何决定扩展位置

- 新增模型可调用动作：注册工具；
- 替换存储或执行环境：提供新的Service Provider；
- 拦截工具或模型请求：监听对应waterfall事件；
- 保存重启后仍需存在的事实：扩展会话事件；
- 只改变一个Agent的能力：在Agent作用域挂载；
- 提供一套可安装组合：制作Bundle，而不是修改Agent Loop。

## 本章小结

Cordis的核心价值是把依赖、作用域和生命周期显式化。插件不是任意脚本；成熟插件必须说明它依赖什么、贡献什么以及如何撤销副作用。

## 思考题

3. 哪些状态应该属于插件实例，哪些应该进入会话事件？
