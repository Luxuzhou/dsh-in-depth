# 第9章 插件生态与生产门禁

## 学习目标

学会按能力而不是热度理解社区生态，能够审查第三方插件，并为企业安装、升级和退出建立可执行门禁。

## 9.1 生态分层

截至本书快照日期，GitHub `dsh-plugin`主题中的项目已覆盖：

- 产品表面：TUI、桌面壳、侧边栏、主题和交互组件；
- 感知能力：视觉、OCR、Web搜索和浏览器操作；
- Agent能力：记忆、多Agent、Workflow、定时任务和回滚；
- 工程能力：Git、代码导航、性能分析和沙箱；
- 业务应用：内容发现、笔记、会议、设计和数据分析。

生态地图只说明探索方向，不代表项目经过统一安全审核。星数、更新时间和README演示都不是生产证明。

## 9.2 十项审查清单

| 项目 | 需要回答的问题 |
|---|---|
| 来源 | 作者、仓库和发布包是否一致？ |
| 许可 | 是否允许企业使用、修改和分发？ |
| 版本 | 是否固定DSH和依赖兼容范围？ |
| 安装 | 是否执行`prepare`或其他安装脚本？ |
| 权限 | 能访问哪些文件、进程、网络和凭据？ |
| 数据 | 输入输出是否离开本机或企业边界？ |
| 失败 | 超时、取消、重试和部分失败如何表现？ |
| 测试 | 是否有单元、集成和真实组合测试？ |
| 维护 | 最近提交、Issue响应和发布频率如何？ |
| 退出 | 卸载后是否清理配置、进程和持久数据？ |

## 9.3 生产接入分级

1. **观察区**：只读源码和文档，不安装；
2. **实验区**：隔离工作区、虚拟凭据和测试数据；
3. **受控试点**：固定提交、最小权限、完整审计、有限用户；
4. **生产允许**：内部构建制品、回归集、漏洞响应和回滚方案；
5. **淘汰**：停止新会话，导出数据，卸载并验证残留。

## 9.4 不要把社区插件变成领域内核

插件适合接入和编排能力。企业的指标口径、权限决策、审计事实和确定性计算应保存在自有服务与版本化配置中。这样第三方插件停止维护时，只需要替换入口，不必重建业务真相。

## 9.5 如何持续更新生态章节

生态快照记录日期、查询方式和选择标准，不把动态星数写成长期结论。每次书籍发布只挑选能代表一种架构模式的项目作为案例，并注明“未审计”“实验验证”或“生产验证”。

建议分类观察：

- 纯UI插件如何使用客户端扩展点；
- 工具插件如何声明Schema和权限；
- 记忆插件如何定义跨会话生命周期；
- Workflow插件如何保存和恢复状态；
- 桌面发行版如何跟随官方Web变化。

## 本章小结

生态价值来自可组合探索，生产价值来自可验证治理。企业需要插件准入和退出机制，而不是一份越来越长的推荐列表。
