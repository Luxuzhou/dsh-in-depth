# 第4章 会话、事件与上下文工程

## 学习目标

理解事件日志为什么是会话真相来源，区分持久事实和实时控制，解释上下文派生、压缩、恢复与分支的正确边界。

## 4.1 聊天记录不是完整会话

传统聊天只保存用户与助手文本。Agent系统还需要保存工具调用、工具结果、turn和step边界、模型用量及可回放的上下文变更。DSH采用仅追加的SessionEvent日志，再从日志投影出模型历史、UI transcript、遥测和恢复状态。

核心原则是：**凡是模型可见的信息，都必须能从会话日志重建。** 如果插件直接修改内存提示却不记录事件，重启、回放和调试就会看到不同世界。

## 4.2 三类状态

| 状态 | 示例 | 保存方式 |
|---|---|---|
| 持久事实 | 用户消息、工具结果、压缩摘要 | SessionEvent |
| 实时控制 | inbox、运行状态、取消信号 | `agent/*`事件和内存状态 |
| 外部世界 | 文件、数据库记录、远程任务 | 外部系统及其审计日志 |

会话日志并不会自动成为外部世界的事务日志。工具已经修改数据库后，即使删除聊天记录也不会撤销业务副作用，因此高风险工具需要幂等键、审批和补偿机制。

## 4.3 从事件派生模型历史

模型请求前，系统从日志中选择需要的用户消息、助手消息、工具调用和工具结果。派生过程可以隐藏对模型无意义的流式片段，但必须保持语义顺序和调用配对。

上下文压缩不是把旧消息随意删掉，而是创建一个新的、可记录的替代表达。压缩后需要回答三个问题：压缩覆盖到哪个事件边界，保留哪些工具证据，如何在失败时恢复原请求。

## 4.4 Skill目录为什么也要进入日志

可用Skill会随工作区和插件变化。若模型在某一步看到一个Skill目录，后续回放却使用当前目录，就无法复现当时决策。DSH的Skill消费者把模型可见目录写入持久用户角色消息；完整Skill正文按需加载，减少上下文占用。

这体现了渐进式披露：先给模型短目录，选择后再加载正文和明确引用的资源，而不是把全部知识一次塞入系统提示。

## 4.5 多轮业务状态不能只依赖Transcript

对于智能问数、客服或审批应用，应在会话之外维护结构化业务状态：目标、指标、过滤条件、已解析实体、歧义、假设和审批状态。每个字段记录来源轮次和置信状态。

```json
{
  "goal": "科室检验量同比",
  "metric": {"id": "inspection_item_count", "status": "confirmed"},
  "filters": {"patient_type": "outpatient"},
  "time": {"mode": "year_over_year"},
  "ambiguities": [],
  "approval": "pending"
}
```

Transcript提供语言证据，结构化状态提供业务约束。两者需要关联，但不能互相替代。

## 4.6 Fork、恢复与长期记忆

会话Fork适合从某个历史边界探索不同方案；恢复适合进程重启后继续同一会话；长期记忆则跨会话保存用户偏好或知识。三者生命周期不同，不能把“会话持久化”误称为“长期记忆”。

## 本章小结

会话日志提供可回放事实，实时事件提供控制，外部系统保存真实副作用。生产应用还需要结构化业务状态，避免模型每轮重新猜测用户意图。
