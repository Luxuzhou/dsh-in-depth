# 第7章 Skills、MCP、Workflow 与 Subagent

## 学习目标

理解DSH的多种扩展机制分别解决什么问题，能够为一个新需求选择最小合适机制，而不是把所有能力都写成插件或工具。

## 7.1 四种扩展机制

| 机制 | 主要作用 | 适合内容 |
|---|---|---|
| Plugin | 改变运行时能力和生命周期 | 服务、策略、UI、Provider、工具 |
| Skill | 按需加载的操作知识 | SOP、领域说明、脚本使用方法 |
| MCP | 跨进程暴露工具和资源 | 外部系统适配、跨Harness复用 |
| Workflow | 可复现的多步执行 | 固定流程、后台任务、结构化产出 |

Subagent不是第五种知识格式，而是把工作委派给另一个Agent执行上下文的协作能力。

## 7.2 Skill：渐进式披露知识

Skill目录先向模型暴露名称和简短描述；模型选择后才加载完整正文。这样可避免系统提示随技能数量线性膨胀。DSH支持项目级、用户级、自定义和Bundle提供的Skill来源，并通过优先级与作用域决定同名Skill的赢家。

Skill适合描述“如何完成任务”，不适合保存高频变化的业务真相，也不应承载必须强制执行的权限。模型可能不调用Skill，因此安全规则必须位于工具策略或业务服务。

## 7.3 MCP：跨边界复用能力

MCP把外部进程或远程服务的工具、资源和提示暴露给Agent。它适合复用已有数据库网关、浏览器、研发平台或企业API，但协议连通不代表生产安全。

接入MCP Server前应审查：认证方式、工具Schema、传输边界、超时取消、返回大小、日志敏感信息、版本兼容、租户隔离和服务不可用时的行为。

## 7.4 Workflow：把确定步骤从模型中拿出来

如果任务流程已知且每一步都应执行，就不应让模型每次重新发明顺序。Workflow可以把确定步骤、输入输出Schema和失败恢复固化，模型只负责选择流程或填充高层参数。

```text
用户目标
  → Agent选择“月报生成”Workflow
  → 固定步骤：取数 → 校验 → 制图 → 生成草稿
  → 人工审批
  → 发布
```

这是一种混合自主性：目标解释可以开放，关键业务流程保持确定。

## 7.5 Subagent：隔离上下文而不是制造热闹

子Agent的价值是任务分解、上下文隔离和并行专业化。它也会引入协调成本、重复工具调用、结果冲突和更高费用。只有当子任务可以独立验证，或确实需要不同权限、模型和上下文时，委派才有明确收益。

## 7.6 选择决策树

```text
需要改变DSH运行时？ ─是→ Plugin
          │否
只是提供按需知识/SOP？ ─是→ Skill
          │否
能力已在外部进程或平台？ ─是→ MCP
          │否
步骤固定且需可靠复现？ ─是→ Workflow
          │否
任务可独立验证并值得隔离？ ─是→ Subagent
```

实际项目可以组合，例如Plugin注册一个MCP Provider，Skill教模型何时使用，Workflow固化高风险流程，Subagent负责独立审查。

## 本章小结

扩展机制没有高低之分，只有边界是否匹配。把强制规则写进Skill、把固定流程交给自由Agent、把内部实现直接暴露为MCP，都会增加不必要风险。
