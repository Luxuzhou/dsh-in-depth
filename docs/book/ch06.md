# 第6章 Plugin、Bundle 与 Profile

## 学习目标

区分运行插件、Bundle和Profile，理解配置层叠顺序，并能把本地插件打包为可安装、可覆盖、可卸载的发行单元。

## 6.1 三个概念

- **Plugin**是运行时模块，通过`apply(ctx)`注册能力。
- **Bundle**是带`dsh.bundle`声明的npm包，交付一层`cordis.patch.yml`组合配置。
- **Profile**是用户机器上的可运行装配，按顺序列出Bundle，并保存自己的覆盖层和依赖。

一个包不能同时既是Bundle又是Profile。作者发布Bundle，用户启动Profile。

## 6.2 配置如何叠加

有效配置从空树开始，按顺序应用：

1. Profile列出的Bundle层；
2. Profile自己的`cordis.patch.yml`；
3. DSH Home级覆盖；
4. 命令行传入的`--patch`覆盖，按参数顺序。

后层按行ID覆盖前层。需要特别注意：patch会替换该行的整个`config`，不是深度合并某几个键。用户只改一个字段却漏写其他字段，可能导致配置静默丢失，因此审查有效配置要使用：

```bash
dsh --profile web --dump-config
```

## 6.3 配置必须可验证

插件可导出同名`Config`类型和Schemastery Schema，让无效配置在加载阶段失败，并由Schema提供默认值。凡是不同部署可能选择不同值的超时、端点、限额和开关，都应成为配置，而不是硬编码常量。

凭据不应直接放在公开patch中。生产部署还要考虑密钥引用、轮换、日志脱敏和不同Profile之间的隔离。

## 6.4 一个Bundle的最小结构

```text
dsh-example-plugin/
├── package.json
├── cordis.patch.yml
└── index.js
```

`package.json`声明：

```json
{
  "name": "dsh-example-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": {"bundle": {"patch": "./cordis.patch.yml"}}
}
```

安装后，`dsh plugin --profile demo add ...`将依赖和Bundle层加入Profile；移除命令应同时撤销依赖与组合层。

## 6.5 从Git安装的供应链风险

Git依赖下载的是源码。TypeScript包通常需要`prepare`脚本生成构建产物，而现代pnpm要求用户显式允许依赖在安装时执行构建脚本。这个允许意味着“让第三方代码在Agent沙箱之外、安装阶段运行”。

因此企业应：审查源码和许可证、固定提交SHA、生成SBOM、限制安装来源、在隔离环境构建，并优先使用带签名或内部镜像的预构建制品。

## 6.6 HMR与生命周期

配置变化可能热替换插件。旧实例的工具、事件和连接必须完整清理，新实例再按验证后的配置挂载。一个开发期看似无害的资源泄漏，在长期运行Web服务中会演变成重复执行和内存增长。
