# 第5章 工具、审批与安全策略

## 学习目标

能够编写一个类型化工具，理解工具Schema、规范值、模型内容和UI展示的区别，并设计执行前、执行中和执行后的安全策略。

## 5.1 工具是受治理的动作接口

工具描述告诉模型“什么时候用”，参数Schema限制“以什么数据调用”，执行函数决定“真实世界发生什么”。一个生产工具还需要取消、超时、权限、审计、幂等和结果大小控制。

官方工具DSL的最小形式如下：

```ts
import { defineTool } from '@deepseek-ai/dsh-tools'

defineTool({
  name: 'greet',
  description: 'Greet someone by name.',
  parameters: {
    name: { type: 'string', required: true },
  },
  output: {
    schema: { type: 'string' },
    render: (_args, value) => [{ type: 'text', text: value }],
  },
  async execute(args) {
    return `Hello, ${args.name}!`
  },
})
```

`execute`返回规范值；`render`将其转换为模型可见ContentBlock。把两者分开，有利于测试、日志和不同客户端展示。

## 5.2 工具描述决定模型策略

描述应说明适用条件、禁止条件和输出语义，而不只是重复工具名。参数应表达业务概念，避免让模型传递内部表名、SQL片段或文件系统实现细节。

较好的Data Agent工具参数是`metric_id`、`time_range`和`filters`；较差的是让模型直接填写任意`sql`。前者把错误限制在受治理语义空间，后者把数据库权限交给概率模型。

## 5.3 执行流水线

DSH工具运行时提供多层介入点：

```text
模型调用
  → 参数解析与可见性检查
  → tools/pre-execute：允许 / 拒绝 / 请求审批
  → monotonic guards：只能增加拒绝，不能覆盖其他拒绝
  → tools/execute：超时、重试、指标包装
  → 工具本体
  → tools/post-execute：接受、替换、补充或阻断结果
  → tools/result：观察最终冻结结果
```

审批不是一个弹窗，而是pre-execute中的策略决定。若当前表面不支持审批，“ask”必须安全失败，而不是默认为允许。

## 5.4 风险分级

| 风险 | 示例 | 推荐策略 |
|---|---|---|
| 只读低风险 | 读取公开文件 | 自动允许，限制大小 |
| 只读敏感 | 查询患者记录 | 身份鉴权、字段脱敏、审计 |
| 可逆写入 | 创建草稿 | 展示差异，可撤销或确认 |
| 外部影响 | 发消息、执行付款 | 明确审批、幂等键、限额 |
| 高危不可逆 | 删除生产数据 | 默认拒绝或专用人工流程 |

不能只按工具名授权。同一个Shell工具既能运行测试，也能删除文件；策略需要结合参数、工作区、用户、Agent作用域和当前审批上下文。

## 5.5 取消、超时和重试

取消信号应贯穿策略监听器、工具包装器和工具本体。超时后后台工作若继续运行，用户可能认为操作失败后重试，实际产生两次副作用。写操作重试前必须有幂等标识或可查询的执行状态。

## 5.6 工具展示也是接口设计

DSH允许工具声明generic、terminal、diff、search、read或web等展示意图。它不是装饰：用户审批一个文件修改时必须看到准确diff；搜索结果被截断时UI必须明确显示不完整，不能让部分结果伪装成全部结果。

## 本章小结

生产工具的核心不是`execute()`，而是清晰语义、最小权限、执行策略、可取消副作用和可验证展示。

## 思考题

1. 为什么“数据库只读账号”仍然不足以保证安全？
2. 哪些错误可以自动重试，哪些错误重试会扩大损害？
3. 工具结果应当何时截断，完整结果又应保存在哪里？
